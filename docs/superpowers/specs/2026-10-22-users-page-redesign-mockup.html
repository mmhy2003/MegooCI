Option B, revised

Two changes since the first version. Projects are now one alphabetical list of names, so "Console Production" and "Console Staging" end up next to each other without the page guessing which is which. "Admin" is now a single choice instead of a flag plus a role. The box below shows what I found in the code and why I'd merge the two.

Admin flag vs "admin" role: what the code actually does

Today: two separate switches

  • "Make admin" sets a yes/no flag on the account. The sidebar admin pages (Users, Integrations, Backups), the admin settings tabs and admin alerts (agent offline, backup failed) go only to flagged users.
  • "Assign role → admin" gives the admin role. The server treats it as full admin for every API, MCP and token call, but the UI hides the admin pages because the flag isn't set.
  • The two only match when a user is created. After that they drift:
    • "Remove admin" clears the flag but leaves the role, so the person still has full admin through the API.
    • "Create user → Admin" sets the flag but gives no role.

Proposed: one "Administrator" switch

  • The page shows one choice per person: Administrator (everything, every project) or Member (only the projects listed).
  • Turning Administrator on or off sets both the flag and the role together, so they can't drift again. Users who have drifted already are fixed once, as part of this change.
  • "Assign role" and the global role chips go away. The roles left (developer, viewer) are only given per project.
  • A member who still has an old global viewer or developer role, which silently lets them see every project, gets a warning with a one-click fix (example below).
